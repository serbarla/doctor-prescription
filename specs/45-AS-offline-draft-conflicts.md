## 1. Objectives and scope

- [ ] 1. Add authoritative draft concurrency control — requirements: use a server-issued monotonic revision (not a wall-clock timestamp) for each prescription draft, changed atomically by every header and item mutation including add, delete and reorder. Persist each local draft's last acknowledged base revision and carry it with offline changes. Server checks expected revision and draft status in the same transaction as each mutation, returning a structured conflict and current authorized draft on mismatch, not a generic retryable string. Do not expose another clinic's data; preserve existing role checks and signed immutability. Handle normal online writes and multiple queued local edits coherently, including locally created drafts and create replay.
- [ ] 2. Detect before destructive replay or cache replacement — requirements: retain a durable local working version, its acknowledged base and ordered pending operations; compare against authoritative current revision before replay. If both diverged, stop all dependent operations for that prescription and persist a visible conflict with both current server and local draft values including medication order/deletes; do not overwrite either or mark failed/synced as a side effect of merely detecting it. Unrelated entities may continue safely. Cache refresh, SSE/polling, offline restart and local retention must not evict, overwrite or hide a pending/conflicted version. For old unsynced outboxes lacking a trustworthy base, preserve them and require explicit review rather than assume no conflict; migrate existing local/server databases without data loss.
- [ ] 3. Implement explicit resolution on the existing desktop prescription/sync surface — requirements: present accessible `es-EC` labels, local versus server content and choice: use server or apply local; cancel leaves both intact and visibly unresolved. Choosing server is explicit confirmation before retiring superseded pending draft operations and installing the fetched server version in one local transaction. Choosing local submits the complete intended header and item set as one server-side compare-and-swap against the revision displayed to the user; do not replay stale intermediate writes or silently merge. Only after acknowledged success atomically update local base/cache and retire corresponding operations. If server changes again, retain local and show a fresh conflict for a new choice. Preserve earlier queued dependent sign operations until safely reconciled; never auto-sign a chosen version without a valid explicit sign action and the snapshot guarantees of 44-AR.
- [ ] 4. Enforce signed server wins — requirements: if the authoritative prescription is signed, voided or superseded at detection, choice or write time, reject draft writes atomically and load the server record as authoritative, without presenting an option to overwrite it. Preserve unsent local edits and any offline-signed provisional snapshot durably as a clearly labeled, non-authoritative local recovery copy; do not silently discard, renumber, mutate the issued server record, replay a stale sign, or call the local copy issued. Provide a user-visible route to inspect/copy its contents into a new draft through normal authorization and validation, with fresh identity and no automatic signing; keep number-block consumption/burn and rejection visible. Prevent cache refresh and eviction from removing this only copy.
- [ ] 5. Implement deterministic `draft_conflict` behavioral regression tests in the existing Rust source test modules for both server and desktop features, using isolated SQLite and synthetic fixtures; test real persistence, atomic mutation and replay/resolution boundaries, not only serialization. Document the user resolution and upgrade/recovery behavior in `persona-sanus/README.md`.

### Out of scope / no-go

- No automatic field-level merge, last-writer-wins for divergent drafts, deletion of unsynced edits, cross-clinic data exposure, or overwriting a signed document. No PHI in logs, public sync notifications or conflict identifiers. Keep outbox, local DB and snapshots within current private storage/session controls.
- No new general-purpose collaboration system or patient/template conflict policy. No edit to context or other specs; do not change spec 44's issued-snapshot guarantees. If additional files or a different product decision are necessary, stop that portion and request project-owner approval.

## 2. Problem and decision

- Problem: the desktop outbox replays header and item mutations independently, and refresh skips rows with pending outbox work; no common draft revision detects another client's edits. Replay can overwrite a newer draft or replay into a record already signed elsewhere.
- Decision: established product rule is server wins for signed data and an explicit choice for concurrent in-progress drafts. Recommended implementation is revision-based compare-and-swap, durable local conflict state and a full-draft atomic resolution; a recovery copy protects otherwise unsent content without overriding the signed record. These mechanics are design recommendations, not additional established product policy.
- Open questions: None. The project owner decides any divergence or scope change.
