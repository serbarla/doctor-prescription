## 1. Objectives and scope

- [ ] 1. Adopt **recommended** mandatory TOTP for doctors and administrators, resolving the conflict between PRD §9's MFA requirement and architecture §4's currently implemented optional enrollment. Nursing and secretary retain their existing sign-in policy. Use server-side current membership as role authority; do not infer assurance from client state. No unconditional full session on initial clinic-admin signup, unenrolled privileged sign-in, promotion, or other session-creation/rotation path. Preserve expiring sessions and device-revocation checks.
- [ ] 2. Implement a short-lived, single-use, purpose-bound restricted authentication state after successful password authentication for required-role users without an enabled factor. It must allow only enrollment initiation/confirmation, necessary status and sign-out, and recovery as explicitly specified below; it must not authenticate as a normal cookie, reach `/api/me`, data, PDF, sync, device registration, mutations, or any other protected API, nor be exchanged for a full session without a valid confirmation. Bind the state to user and purpose, rate-limit attempts with the existing auth limit, enforce expiry, and rotate/invalidate its credential atomically upon successful confirmation. Never place tokens, TOTP secrets, codes or recovery codes in URLs, logs, audit metadata, persistent browser storage or desktop cache. Deliver setup secret/URI only over the existing secure response flow and render once; protect responses from caching. Repeated enrollment must not overwrite or disable an already enabled factor, even with an existing session; abandoned/expired setup cannot affect an enabled factor.
- [ ] 3. For enrolled required-role users, password sign-in produces only an expiring, purpose-bound challenge; invalid, expired, replayed or concurrently redeemed challenge cannot obtain a session. A valid TOTP promotes via a fresh token, invalidating the challenge; verify current role, factor and account/device state at promotion, not just at password time. Preserve generic errors and server-side throttling; neither ordinary `get-session` nor the actor resolver may accept challenge/setup credentials. Prevent replay of a used TOTP step across concurrent challenges for the same factor, including confirmation, by storing the last accepted time step atomically. Password changes, session refresh and enrollment endpoints cannot grant or preserve a bypass.
- [ ] 4. Migration and role changes fail closed without destroying accounts or clinical data. On rollout revoke existing privileged sessions (including preexisting sessions with enabled factors whose assurance is unknown); require password plus challenge for enabled accounts, or restricted enrollment otherwise. Enforce this even for old-format sessions and on every authorization boundary. On a role change into doctor/administrator atomically revoke that user's sessions and outstanding setup/challenge credentials, including a formerly nonprivileged session; enabled factors require a fresh challenge, absent factors require enrollment. On demotion/removal revoke sessions and outstanding tickets as well; no stale privileged access. Handle first administrator bootstrap, later promotions, concurrent requests and restart consistently. Migrate existing enabled TOTP secrets intact; pending unenrolled setups may be invalidated. Supply reversible schema migrations where practicable without rolling back clinical data, and document that rollback relaxes enforcement and requires session revocation.
- [ ] 5. Provide a usable but non-bypassing lost-factor recovery path: **recommended choice** generate a small set of cryptographically random, single-use recovery codes at enrollment, show them once and store only salted secure hashes; replacement/regeneration requires a fully MFA-verified session and invalidates old codes. A password-authenticated recovery ticket plus one unused valid code atomically consumes it, revokes all sessions and tickets, disables the old factor, and issues only a short-lived restricted enrollment credential; the user must enroll and confirm a new factor before access. Existing enrolled users receive codes at their first successfully challenged session; until provisioned, direct them to the documented offline administrative identity-verification procedure below, not a password-only reset. For lost codes and authenticator, document a controlled operator-only offline recovery procedure requiring independently verified identity and authorized approval, with an attributable audit record, no network reset endpoint, revocation of all sessions/tickets and forced reenrollment; never imply this verification is automated. Remove password-only MFA disable for required roles; no endpoint may overwrite, disable or replace an active factor without the required assurance. Clearly show that recovery codes are sensitive and irrecoverable after display. No secret or code in audit records.
  Implement the operator recovery as a local-only administrative command in the server binary, not direct undocumented SQL: require target user ID, operator identity and approval reference, require exclusive operator access to the database, and atomically clear the factor and recovery codes, revoke all sessions/tickets, and append a secret-free audit event. The next password login enters restricted enrollment, never a normal session. Document exact invocation and independent identity/approval checks; exercise the command against a temporary database in the gate, including failure/rollback. The command does not itself claim to verify identity.
- [ ] 6. Implement isolated deterministic tests in `persona-sanus/src/mfa_enforcement_tests.rs`, registered from `main.rs`, using temporary SQLite databases, real auth/actor/HTTP boundaries, injected clock or fixed TOTP time, and disposable synthetic accounts. Cover signup bootstrap, unenrolled login/enroll/confirm, already-enrolled login/challenge, denied protected endpoints including PDF/sync, bad/expired/replayed tickets, wrong and reused TOTP steps, simultaneous redemption, repeated enroll/disable attempts, recovery and one-use recovery codes, old sessions and schema migration, role promotion/demotion and concurrent requests, cookie rotation, sign-out and unaffected nursing/secretary. Assert state and response content, including no secret exposure. Update owned context and README with the recommendation, conflict, rollout, recovery, offline limitation, and rollback warning.
- [ ] 7. Update login and profile flows to present forced enrollment, challenge, recovery-code display and restricted recovery without suggesting a bypass. Handle cancellation, expiration, incorrect code, reload and network failure without storing credentials or displaying protected data. Preserve the existing visual/accessibility conventions and use `es-EC` copy. Offline: never grant a new privileged sign-in or enroll/challenge/recover without the server; a locally cached earlier session must not bypass enrollment or fresh authentication after this rollout. Keep unsynced work intact and explain how to reconnect; do not silently delete local-only records.

### Out of scope / no-go

- No SMS, email reset, social login, external MFA provider, legal/compliance certification, or recovery based only on a password or clinic role. Do not log secrets, recovery codes, session tokens or clinical data.
- No remote operator bypass or fallback to optional MFA if service/database is unavailable. Preserve existing TOTP factors and offline outbox data.

## 2. Problem and decision

- Problem: `sign_in` currently requires MFA only when already enabled; signup and old sessions can obtain normal access without it, and `mfa_enroll` can overwrite an enabled factor. Role changes and password-only disable create further bypass paths.
- Decision: mandatory privileged MFA is a recommended resolution aligned with PRD §9, not a claim that architecture's optional-enrollment description already mandates it. Restricted setup and one-use recovery support enrollment without a full session; lost-factor operator recovery requires human identity verification and approval.
- Open questions: None for the specified choice; the project owner decides any necessary change in recovery or owned scope.
