## 1. Objectives and scope

- [ ] 1. Unify desktop PDF actions on prescription list and A4 preview — requirements: replace desktop API-only links and the provisional button's automatic app-data write with explicit Save as PDF, Open PDF and Print actions, while preserving web behavior. Build the same `pdf::PdfInput` from the correct prescription's complete pinned document, variables, ordered medications, margins, issue metadata and verified cached image bytes. Use the shared Rust `printpdf` renderer, never HTML print. Final/superseded/voided cached documents retain their own immutable version and verification code; pending/failed unsynced signatures always render provisional, never pretend server acceptance. If required source data, pinned assets, verification code or cached configuration is unavailable or corrupt, fail visibly without producing a misleading PDF; do not fetch during an offline action. No action for draft. Respect existing signed-data/role access and do not fall back to cached PHI on an authorization failure.
- [ ] 2. Deliver native actions safely — requirements: only a user click renders; Save uses a native destination chooser, honors cancellation, uses the existing FR-032 sanitized localized filename and does not create an implicit second copy. Open and Print hand the generated bytes to the OS viewer/print flow on macOS and Windows, with an explicit shared-device warning and A4 guidance; report errors and cancellation honestly, never claim a print completed merely because a viewer opened. Use a private, uniquely created app-controlled temporary location with restrictive permissions/appropriate platform access controls, no PHI in its path, no symlink overwrite, and bounded cleanup after the viewer no longer needs it plus cleanup of stale app-owned temporary files on next launch; do not delete user-saved files. If safe lifetime/cleanup cannot be established, fail visibly rather than silently leaving a permanent file. Reuse existing dependencies/platform facilities where possible.
- [ ] 3. Preserve reconciliation and retention — requirements: local-only/pending/failed rows are never evicted or treated as expired. Recent server-backed final rows can render offline from their cached immutable inputs and stored opaque verification code; a cache miss or expired evicted server-backed row requires connection and is never rendered from incomplete inputs. Online regeneration uses the server path when local data is unavailable. After a successful sync, refresh the authoritative record and regenerate on the next explicit action with its assigned verification code; a rejected sync remains provisional. Never mutate the outbox, numbers, signed records or retention policy merely to render.
- [ ] 4. Add deterministic behavioral regression tests named with `offline_pdf_actions` and document the user/administrator workflow in `context/runbook.md` — requirements: tests exercise action dispatch with isolated temporary data and injectable native/network boundaries; assert actual rendered PDF content/QR semantics and bytes delivered, no network for cached offline actions, no file on cancel/failure, cleanup and cache/retention behavior. Cover both list and preview dispatch, not only a helper. Document OS encryption prerequisite, chooser, viewer cleanup limitation and actionable failures; do not claim secure erasure.

### Out of scope / no-go

- No server-side PDF byte storage, background generation, third-party sharing, QR containing PHI, or app-level database encryption (PRD §9). Do not change signing/sync authority or retention thresholds; never delete an unsynced row.
- Do not alter user-selected saved files during cleanup; do not log PDF bytes, patient information, verification URL or sensitive filenames. Do not ship a fake viewer/print success path. Any newly essential unowned file requires a scope decision.

## 2. Problem and decision

- Problem: list and preview PDF/print links target the server even offline; the separate provisional action writes silently into app data and cached final output has no equivalent local action (`src/main.rs:5868–5900, 7037–7110`).
- Decision: recommended implementation is one desktop action path backed by the existing renderer and cache, with explicit native handoff and controlled temporary files; keep the existing web endpoints. Offline provisional status and QR restrictions are established product decisions, not new ones. Existing caches must remain readable; add a backward-compatible local migration only if needed for authoritative final-code/input caching, with no fabricated code for old records.
- Open questions: None for implementation. If a target OS cannot provide safe handoff/cleanup, record a blocking divergence for the project owner rather than weakening privacy.
